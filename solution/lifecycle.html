Chapter 2 · Mission Lifecycle

From raw goal to verified result
— or an honest surrender

Every mission travels the same seven stages. Two review gates guard the pipeline — one on the way into execution, one on the way out — and at any point the mission can branch to the surrender path, which is a deliverable in its own right, not a failure to deliver.

The seven stages

Stage 1 · Intake — mission becomes task zero

No mission starts without its own contract. The intake dialogue interrogates the requester until the mission has testable success criteria, explicit scope boundaries, an autonomy-dial setting, and an effort budget. Ambiguities are surfaced as explicit open questions — never silently assumed away; if the dial permits, low-stakes ambiguities may be carried into the run as flagged assumptions, escalated the moment they start to matter. This stage exists because the evidence is brutal: bad specification is the single largest failure source in multi-agent systems (44% in the MAST study), and "failing to ask for clarification" is a measured top-ten failure mode. The mission contract is task zero — the root of the tree, judged at delivery exactly as every other task is judged.

Stage 2 · Decomposition — the tree is built, contract by contract

The Orchestrator recursively splits the mission into subtasks, guided by decomposition templates from the Asset Registry — reusable "how to split this kind of work" recipes that are themselves learnable assets. Every node it creates is born as a full contract (anatomy below). Splitting continues until each leaf carries exactly one responsibility with one verifiable outcome — and no further. Dependencies between siblings are declared at creation time, so the tree is really a tree plus a typed dependency graph, and anything not dependent on anything else is free to run in parallel.

Crucially, atomization is a weapon to aim, not a reflex. At every node the Orchestrator applies the decompose-or-delegate gate: work that is inherently sequential and constraint-entangled is measurably damaged by splitting (−39% to −70% in controlled studies), so such subtrees are deliberately kept whole and handed to a single agent with a larger budget. The gate's decision — split or keep — is itself recorded, reviewable, and learnable.

Gate A · Atomicity review — the task graph is the first deliverable

Before any worker exists, the Reviewer audits the decomposition itself: Is each task truly atomic? Is every contract testable as written? Are boundaries non-overlapping and exhaustive? Are stopping conditions present? Are cross-cutting decisions pinned wherever siblings must fit together? Was the decompose-or-delegate gate applied sensibly? A rejected decomposition goes back to Stage 2 with a structured verdict. This is the design's answer to the largest documented failure class — specification errors are caught while they are still cheap, on paper, before they become a thousand misdirected executions.

Stage 3 · Staffing — reuse first, creation second

The Agent Creator clusters the approved tasks into capability categories — groups solvable by the same kind of specialist — so a thousand tasks might need twelve designs, not a thousand. For each category it searches the Asset Registry for proven designs whose capability descriptions match; candidates effectively bid with their track record on similar work. Only where no design can credibly serve the category — a no-bid — does it design a new specialist: role instructions, capability manifest, what context it may request, and the validation harness that will later decide whether the design earns permanence. A systematic pattern of no-bids across the tree is an early surrender signal: the swarm can tell it lacks the capability for a mission before burning the budget discovering it the hard way.

Stage 4 · Execution — contracts, broker, budgets, stall counters

Workers execute their contracts in parallel wherever the dependency graph allows. Each worker sees its contract and nothing else; extra context comes only through the Context Broker, logged. Before starting, a worker must restate its task and surface ambiguities — a contract it cannot restate is a contract it must bounce back, not improvise around. Budgets bind in both directions: a floor that prevents drive-by shallow work, a ceiling that prevents runaway effort. A per-task stall counter watches for no-progress loops — the same task attempted the same way twice triggers the escalation ladder rather than a third identical attempt.

Gate B · Completion review — two tiers, scaled to blast radius

Every delivered task is verified in two tiers. Mechanical: do the contract's testable criteria pass — checks that execute, not opinions? Semantic: does the output actually serve the parent's intent — the tier that catches the program that compiles but plays chess wrongly? Verification depth scales with blast radius: an output that many downstream tasks depend on gets redundant independent execution and consistency checks (multiple runs must agree — a lucky pass is not a pass), while a low-stakes leaf gets a single rigorous check. Suspicious structure — output that fits the letter of the criteria too neatly while smelling nothing like the work — is red-flagged and discarded even if it technically passes. Every verdict is structured: which criterion failed, at which step, in which error class. Verdicts are the audit trail's most valuable records: they drive the escalation ladder now and the Learning Agent later.

Stage 5 · Fold-up — integration is the tree in reverse

As leaves complete, each parent assembles its children's verified outputs into its own deliverable — reconciling, smoothing, and resolving what the pinned decisions didn't prevent. The parent is the single writer for its assembly. A conflict it cannot reconcile is not hand-waved: it becomes a new task (with its own contract) or climbs the ladder. Then the parent's own output faces Gate B like everything else, and the wave rolls upward until the root task — the mission itself — is assembled.

Stage 6 · Delivery — the mission meets its own contract

The assembled result is verified against the mission contract from Stage 1 — the same two tiers, at maximum rigor. What ships to the requester is the result plus its pedigree: what was done, what was verified and how, which assumptions were flagged, what the mission cost against its budget. Depending on the dial, delivery may include the human checkpoint negotiated at intake.

Stage 7 · Surrender — a first-class outcome

When escalations are exhausted, criteria prove contradictory, capability no-bids pile up, or the budget can't survive the remaining work, the mission concludes as "not achievable as specified" — deliberately, at thresholds set by the autonomy dial, never by silent stall. The dossier contains: everything that was completed and verified; the precise blockers with evidence; the full escalation history; budget spent versus value delivered; and — most usefully — what would have to change for the mission to become achievable: relaxed criteria, added capability, more budget, a decision from the requester. For the Learning Agent, surrender dossiers are the richest meals in the ledger: each one maps exactly where the swarm's competence ends.

Anatomy of a task contract

The contract is SWARM's atom. Every field exists to kill a documented failure mode — nothing here is ceremony.

Task Contractid · parent · category · depth — full lineage back to task zero
Objective
The one responsibility this task carries, stated so a stranger could execute it.kills: vague delegation → duplicated & misinterpreted work
Acceptance criteria
Testable conditions, written before execution by the level above. The Reviewer checks these — exactly these.kills: superficial verification; moving goalposts; "looks fine" reviews
Boundaries / anti-scope
What this task must NOT do, and which sibling owns each neighboring concern.kills: overlap, duplication, scope creep across siblings
Inputs & pinned decisions
Everything the worker is entitled to, plus parent-made cross-cutting choices (interfaces, formats, conventions) it must honor.kills: integration conflicts from implicit decisions — discovered at fold-up when they're expensive
Dependencies
Which sibling outputs this task consumes; what it may request via the broker.kills: hidden coupling; premature starts on stale inputs
Stopping conditions
What "done" looks like AND what "stop trying" looks like — max attempts, stall limits, give-up criteria.kills: step repetition (15.7% of observed failures) and unaware-of-stopping-conditions loops (12.4%)
Effort budget
Floor and ceiling. Spent effort is logged against the task; escalation rungs each carry their own cost.kills: runaway spawning; drive-by shallow work; unaccountable cost
Escalation policy
Which ladder applies, per error class; where the human sits per the autonomy dial.kills: blind identical retries; failures that die silently
Verification plan
Verification depth for this task (single check / redundant runs / consistency requirement), set by blast radius. Never visible to the executing worker in its gameable detail.kills: lucky passes gating big subtrees; score-gaming (43× worse when the scorer is visible)
Audit binding
Every event this task generates carries the contract id — the contract is also the key into the ledger.enables: attribution, replay, per-clause compliance rates, learning

The decomposition tree — down, then up

The escalation ladder

A rejection at Gate B never triggers a blind retry. The Reviewer's structured verdict names an error class, and the error class picks the rung — execution slips start low; planning and specification faults jump straight to re-decomposition, because retrying a task that was specified wrong just burns budget rehearsing the same mistake.

What the requester receives

On success — the result and its pedigree

The assembled deliverable, verified against the mission contract; the record of what was checked and how deeply; every flagged assumption; effort spent against budget; and pointers into the audit trail for anyone who wants to inspect any part of the work down to the individual task.

On surrender — the dossier

Everything completed and verified so far; the precise blockers with evidence; the escalation history showing what was tried; budget accounting; and the "what it would take" section — relaxed criteria, missing capabilities, added budget, or a decision only the requester can make. A surrendered mission can be re-entered at intake with the dossier as its starting context.
